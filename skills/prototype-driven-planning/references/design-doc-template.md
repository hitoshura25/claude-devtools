# Design Doc Template

Use this exact structure for the design doc. Keep section names as-is so future
phases can parse them reliably.

---

```markdown
# Design Doc: <Feature Name>

> Generated by prototype-driven-planning skill
> Prototype reference: `prototypes/<feature-name>/`
> Date: <YYYY-MM-DD>

## Summary

One paragraph: what this feature does, why it's needed, and the core technical
approach validated by the prototype.

## Prototype Reference

What the prototype proved:
- <Key finding 1>
- <Key finding 2>

Prototype location: `prototypes/<feature-name>/`

Key files:
- `<file1>` — <what it demonstrates>
- `<file2>` — <what it demonstrates>

Limitations of the prototype (what it intentionally did NOT cover):
- <limitation 1>
- <limitation 2>

## Architecture Overview

Describe the components needed, their responsibilities, and how they interact.
Reference prototype files that demonstrate each component's behavior.

### Components

For each component:
- **Name**: What it's called
- **Responsibility**: What it does (one sentence)
- **Prototype evidence**: Which prototype file demonstrates this
- **Production considerations**: What changes between prototype and production

### Interactions

How components communicate. If the prototype demonstrated specific interaction
patterns (API calls, message passing, shared state), reference them.

## Data Model

Describe data structures, schemas, and data flow. Include actual shapes observed
by the prototype, not theoretical ones.

If the feature involves external data sources, document:
- The actual response format (as observed by the prototype)
- Any surprises or deviations from official documentation

## Dependencies

List new dependencies this feature introduces. For each:
- **Package/library**: Name and version (from prototype)
- **Why needed**: What it provides
- **Alternatives considered**: If relevant

## Tooling

Validated during prototype build. These exact commands are consumed by downstream
skills — do not change the field names.

### Language & Ecosystem
- **Language**: <e.g., Python 3.11>
- **Package manager**: <e.g., uv, npm, cargo>
- **Service root**: <relative path from project root, e.g., `services/airflow-ingestion/`>

### Lint
- **Tool**: <e.g., ruff 0.4.x>
- **Lint command**: <e.g., `uv run ruff check`>
- **Auto-fix command**: <e.g., `uv run ruff check --fix`> or "Not available"
- **Auto-fix scope**: <e.g., "Import sorting (I), unused imports (F401), upgrade annotations (UP)"> or "N/A"
- **Configuration**: <where config lives, e.g., `pyproject.toml [tool.ruff]`>

### Test
- **Framework**: <e.g., pytest 8.x>
- **Test command**: <e.g., `uv run pytest tests/ -x`>
- **Configuration**: <where config lives, e.g., `pyproject.toml [tool.pytest.ini_options]`>

### Bootstrap
- **Command**: <e.g., `uv sync`> — run from service root after scaffold creates config
- **Trigger**: <what file creation triggers bootstrap, e.g., `pyproject.toml`>

### Notes
- <Any toolchain surprises discovered during prototype validation>

## Testing Strategy

Based on cross-cutting research from Phase 2.

### Unit Tests
- What to test
- What to mock (based on real external dependencies the prototype revealed)
- Fixture patterns needed

### Integration Tests
- What integration points to test
- Required test infrastructure (databases, services, APIs)
- Mock vs real service decisions

### Existing Test Infrastructure
- What the project already has that can be reused
- Any gaps in current test infrastructure

## Containerization

If applicable. If not, write: "Not applicable — <one-line reason>."

If applicable:
- **Base image**: Which one and why
- **Entrypoint behavior**: What the official docs say about how it starts
  (this is technology-specific and cannot be assumed)
- **Environment variables**: What's needed at runtime
- **Health checks**: How to verify the container is ready
- **Build considerations**: Multi-stage builds, dependency caching, etc.

## Security Posture

Specific to this feature's data flows and external interactions.

### Input Validation
- What inputs exist (as revealed by the prototype)
- What validation each input needs and why

### Authentication & Authorization
- What auth patterns are required
- How they integrate with existing project auth (if any)

### Data Sensitivity
- Does this feature handle sensitive data?
- What protections are needed?

### Known Risks
- Technology-specific security gotchas discovered during research

## Deployment Strategy

### Integration
- How this feature fits into the existing deployment pipeline
- New infrastructure dependencies

### Configuration
- New configuration values needed
- Environment-specific considerations

### Rollback
- Can this feature be rolled back independently?
- Are there data migration concerns?

## Open Questions

Things the prototype didn't resolve or that need further investigation before
implementation. Be specific about what's unknown and why it matters.

- <Question 1>: <Why it matters>
- <Question 2>: <Why it matters>
```
