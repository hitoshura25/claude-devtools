# Task Document Template

This is the reference template for individual task files generated by the agent-ready-plans skill. Each task file follows this structure exactly.

---

## Template

```markdown
# Task [NN]: [Task Title]

> **Phase:** [Phase Name from Implementation Plan]
> **Original Task:** [X.Y from plan]
> **Complexity:** [simple | moderate | complex]

## Project Context

[Brief project context block — 10-15 lines max. Same across all tasks in a plan.
Include: what the project does, tech stack, key directory structure, conventions.]

## Objective

[1-2 sentences: what this task accomplishes and why it matters in the overall plan.]

## Prerequisites

[Files that must already exist from prior tasks. Listed for human reference only —
the runner executes sequentially so these will be in place.]

- `path/to/file-from-earlier-task.py` (created in Task NN-1)

## Files to Create

[Listed up front so aider knows which files to work on.]

- `exact/path/from/project/root/file.py`
- `exact/path/from/project/root/test_file.py`

## Files to Modify

[If this task modifies existing files instead of creating new ones.]

- `exact/path/to/existing.py` (lines ~120-135)

## Instructions

### Step 1: [Action — e.g. "Create the test file"]

Create `exact/path/to/test_file.py` with this content:

\```python
# exact/path/to/test_file.py
"""Tests for the specific module."""

import pytest


class TestSpecificBehavior:
    """Tests for SpecificClass."""

    def test_does_the_thing(self):
        """Should do the expected thing."""
        from module.path import SpecificClass

        instance = SpecificClass()
        result = instance.do_thing("input")

        assert result == "expected_output"
\```

### Step 2: [Action — e.g. "Create the implementation file"]

Create `exact/path/to/file.py` with this content:

\```python
# exact/path/to/file.py
"""Module for specific functionality."""


class SpecificClass:
    """Does the specific thing."""

    def do_thing(self, input: str) -> str:
        """Do the thing.

        Args:
            input: The input value

        Returns:
            The expected output
        """
        return "expected_output"
\```

### Step 3: Commit

\```bash
git add exact/path/to/test_file.py exact/path/to/file.py
git commit -m "feat(scope): add specific feature"
\```

## Lint & Test Commands

\```bash
# Lint (run after creating files)
ruff check exact/path/to/file.py exact/path/to/test_file.py

# Test (run after implementation)
cd services/service-name
python -m pytest tests/test_file.py -v
\```

## Verification Checklist

After completing this task, confirm:

- [ ] File exists: `exact/path/to/file.py`
- [ ] File exists: `exact/path/to/test_file.py`
- [ ] Tests pass: `python -m pytest tests/test_file.py -v` (expected: 1 passed)
- [ ] Git commit created with message: `feat(scope): add specific feature`
```

## Section Details

### Project Context

Extracted once from the design document and repeated verbatim in every task file. Keep it tight — this eats into the small model's context window.

**Good context block:**
```
This project adds an Apache Airflow service that downloads Health Connect
exports from Google Drive, parses the SQLite database, and feeds records
into an existing MinIO + RabbitMQ pipeline.

Tech stack: Python 3.11, Apache Airflow 2.8, Pydantic, pytest, structlog
Directory: services/airflow-ingestion/
Patterns: TDD (test first), Pydantic Settings, abstract base classes for extractors
Naming: snake_case files, PascalCase classes, conventional commits
```

**Bad context block (too verbose):**
```
This is a comprehensive healthcare data platform that processes data from
multiple wearable devices including Oura Ring, Dexcom Stelo CGM, and Samsung
Health. The platform uses a microservices architecture with Docker Compose
orchestration, featuring MinIO for object storage, RabbitMQ for message
queuing, PostgreSQL for metadata, and a custom ETL narrative engine that
transforms raw health records into training data for AI models. The system
supports both direct API uploads and batch processing...
[continues for 30 more lines]
```

### Files to Create / Modify

Listed explicitly at the top so aider's file-tracking knows which files are in scope. Aider performs best when it knows upfront which files it's working with.

### Instructions

Each step is a single action. The step title should be a verb phrase:
- "Create the test file"
- "Create the implementation"
- "Add the import to __init__.py"
- "Commit"

Code blocks must be complete — never use `...` or `# TODO` or "implement similar to Task 3.1". The whole point is that the small model doesn't need to reason about what goes there.

### Lint & Test Commands

Concrete commands with `cd` if needed. Include expected output when helpful:
```bash
# Expected: 2 passed, 0 failed
python -m pytest tests/test_settings.py -v
```

### Verification Checklist

Human-readable checklist for quick review between tasks. Should be checkable in under 30 seconds by glancing at `git status` and test output.

## Complexity Ratings

Used in the manifest and task headers to set expectations:

| Rating | Description | Example |
|--------|-------------|---------|
| **simple** | Create files, no logic, boilerplate | Directory scaffolding, requirements.txt, Dockerfile |
| **moderate** | One class/module with clear logic, has tests | A record extractor, a parser, a client wrapper |
| **complex** | Multiple interacting components, joins, edge cases | DAG assembly, consumer routing with format detection |

---

## Task Splitting Guidelines

If a single task from the implementation plan would produce a task doc exceeding ~2000 tokens:

1. Split the test and implementation into separate task docs
2. Keep "create file" and "modify file" as separate tasks
3. For tasks with 3+ files, consider one task per file

Example split:
```
Original: Task 5.3 — Heart Rate Extractor (with Series Join)
Split into:
  - 08-task-5.3a-heart-rate-extractor-tests.md
  - 09-task-5.3b-heart-rate-extractor-implementation.md
```

Update the manifest to reflect the split, and keep sequential numbering intact.
